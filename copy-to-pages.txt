Steps:

0. In C:\dev\App run `npm run predeploy`. IT MUST EXIT 0.

   This is a hard gate, not a formality, and it exists because for one phase
   the only thing between a poisoned dist/ and eleven live users was a
   sentence in a document. It now has TWO halves and both must pass.

   THE SOURCE HALF — is this dist/ the thing we think it is. It refuses if:

     - dist/ is older than src/ / public/ / app.json / package.json, i.e. it
       was not produced by the code on disk;
     - anything in dist/ carries the denied build id cfaab51c, the phase-17A2
       artifact that stamps a false Apple Health grant onto every account
       that signs in against a 0013-applied database;
     - the bundle shows any pre-fix fingerprint — healthEnabled defaulting
       true, health_enabled in the synced column map, workouts:[] standing in
       for "not read", or the string "No workouts recorded today".

   THE DESTINATION HALF — is there a safe place to put it. It refuses if the
   Pages working tree is not identical to origin/main:

     - any modified tracked file, staged or not;
     - any untracked file;
     - ahead of, behind, or without an upstream; wrong branch; detached HEAD.

   That half is new, and it is new because on 2026-09-05 the Pages repo held
   21 modified files and two stale 8.7 MB bundles from a copy that was made
   on 31 August and never committed. Step 4 below is "copy and commit". It
   would have carried all 23. A clean dist/ copied into a dirty destination
   still publishes a wrong site.

   If it refuses, STOP. Read what it names, fix that, run it again. Do not
   copy anyway. Nothing below this line is safe to do while it is failing.
   (See scripts/lib/distGuard.mjs and scripts/lib/pagesGuard.mjs for why each
   check is there; scripts/pages-guard.test.mjs demonstrates both halves
   refusing and passing against real repositories.)

1. In C:\dev\App run `npm run build:web`. Confirm it succeeds and that dist/ contains:
   - index.html
   - .nojekyll          <-- MANDATORY. Without it GitHub Pages runs Jekyll,
                            which deletes every path starting with an underscore,
                            and the entire bundle lives under _expo/. The site
                            will load a blank page.
   - 404.html
   - _expo/ (the JS bundle)
   - manifest.json
   - version.json
   If .nojekyll is missing, stop and tell me — do not continue.

2. Wipe the old contents of the Pages repo folder EXCEPT the .git folder.
   Do not delete .git. If the folder only has a README, deleting it is fine.

   This step is what stops old bundles accumulating. The 31 August tree had
   THREE entry-*.js files in _expo/static/js/web for a one-bundle site,
   because a previous run copied over the top instead of wiping first.
   `npm run postdeploy` in step 3b refuses if any of them survive.

3. Copy EVERYTHING from dist into the Pages repo folder, including dotfiles.
   On Windows use robocopy, not xcopy, and not a shell glob:
     robocopy dist <pages-repo-path> /E
   (robocopy exit codes 0-7 mean success, not failure — do not treat 1 as an error.)
   A `dist\*` copy silently skips .nojekyll. That is the one file that breaks the site.

3b. Run `npm run postdeploy`. IT MUST EXIT 0.

   This is the post-condition on the thing about to be published, and this is
   the only moment it can still be caught — after this, step 4 is a commit.
   It refuses unless:

     - every bundle the pages load is actually on disk (an index.html
       pointing at a bundle that is not in the commit is a blank site, and
       that has already happened once here);
     - every bundle on disk is loaded by some page (no orphans from step 2
       not having run);
     - all pages name the SAME bundle (not two builds mixed together);
     - version.json's buildId and bundle agree with what is published;
     - .nojekyll, index.html, 404.html, manifest.json and version.json are at
       the ROOT;
     - every file in dist/ is present in the Pages repo and byte-for-byte
       identical — robocopy skipping a file it believed unchanged is exactly
       how a stale index.html survives a deploy.

   It also re-runs the source half of step 0 against the dist/ you actually
   built in step 1, which is not necessarily the one step 0 looked at.

4. Verify inside the Pages repo folder, by listing the actual files:
